# Forensic audit of the 28 conflicting-evidence findings (v2, seed 0)

Evidence: `sim/out/forensic-A1.json` has all 28 (seller, finding id, raw VIDR row, engine result). It is generated by `FORENSIC=/tmp/forensic.jsonl node sim/run.mjs 1 /tmp/x.jsonl <seller>` for sellers 22, 59, 133, 170, 207, 244, 281, 318, 392, 429, 466 (scenario `amazon_flag_status_conflict`), against the engine at c608611 (unchanged production code). Per seller the raw files are also written by `DUMP=<id> node sim/run.mjs 1 /tmp/one.jsonl <id>`.

## What the 28 are
All 28 are one pattern: `is-amazon-invoiced = TRUE` with `invoice-status = InvoiceUploaded` and an invoice number in the row, business order, shipment in range. The engine raised BOOKS_GAP / NUMBER_AT_AMAZON_NOT_IN_BOOKS, state ACTION_REQUIRED (confident), for each. None was UNDETERMINED. The second pattern in the scenario (FALSE with InvoiceCreatedByAmazon) raised no finding (see "also found").

## Root cause (named, in code)
1. src/reconcile.js line 17: invoice-status is mapped to a state (see the STATUS map near line 10 to 18; InvoiceCreatedByAmazon and CreditNoteCreatedByAmazon to CREATED_BY_AMAZON). This is the only place the engine decides who issued the invoice.
2. src/loop/project.js line 73 at c608611: `const A = rec.docs.filter(d => d.parts['transaction-type'] === 'SHIPMENT' && !d.correction && d.state !== 'CREATED_BY_AMAZON')`. The set of invoices the seller owes is built from the state only.
3. src/loop/project.js lines 215 to 220: for each document in A with no match in the books, `put(... family 'BOOKS_GAP', subtype 'NUMBER_AT_AMAZON_NOT_IN_BOOKS' ...)` as ACTION_REQUIRED.
4. The column is-amazon-invoiced is never read by the loop engine: it is parsed in src/vidr.js line 37 and shown as a column in src/reconcile.js line 340, but nothing in project.js consults it. The engine has no branch for "the two fields disagree".
So when the field says Amazon issued the invoice and the status says Uploaded, the status wins silently and the seller is told to find a number in their books that, per the field, Amazon issued.

## Reproduction
Minimal, no simulation: on c608611, test/ws1-confident-false.test.js from branch fix/ws1-confident-conflict (4b1200c) fails 6 of 8 (the control and the blank-field fallback pass). Run: `git checkout 4b1200c -- test/ws1-confident-false.test.js && node --test test/ws1-confident-false.test.js`.

## Correct behavior required
Fields agree and say Amazon issued (TRUE + InvoiceCreatedByAmazon): no finding. Fields agree and say seller (FALSE + InvoiceUploaded or other seller states): as before. Fields disagree, or the value is not TRUE/FALSE, or rows of one shipment disagree: UNDETERMINED, plus a coverage note saying what conflicted, never a confident finding and never converted into the opposite verdict. A blank field falls back to the status (no change for files without the field).

## Also found
- FALSE + InvoiceCreatedByAmazon (the second conflict pattern): no finding was raised, because the status alone excluded it. That is not an accusation, but it is a silent acceptance of conflicting evidence. The fix on 9682c78 turns it into UNDETERMINED with a note.
- The non-business-order finding (A3 in AUDIT-v2.md) is the same class: a field the loop engine ignores. It is not part of the 28 and is not fixed here.
